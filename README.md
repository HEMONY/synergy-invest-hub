# Synergy — منصة الوساطة العقارية

دليل شامل للمشروع: الفكرة، المستخدمون، سير العمل، البنية التقنية، قاعدة البيانات، الإعداد، والنشر.

---

## 1. نظرة عامة

**Synergy** منصة وساطة عقارية إلكترونية تربط بين:

- **أصحاب العقارات** الذين يملكون عقاراً يحتاج تأهيل وترميم، أو تشطيب، أو يريدون بناء عقار جديد، أو يرغبون في تملّك عقار جديد.
- **الشركات العقارية (المستثمرين)** الراغبة في تمويل هذه المشاريع أو تنفيذها.

وذلك **بإشراف كامل من إدارة المنصة**، التي تراجع كل طلب قبل نشره، وتربط بين الطرفين، وتتابع تقدّم المشروع حتى اكتماله.

المنصة عربية بالكامل (RTL)، وتدعم الوضع الليلي/النهاري.

## 2. الفئات المستخدمة (User Roles)

| الفئة | ماذا تفعل على المنصة |
|---|---|
| **صاحب عقار (Owner)** | يقدّم طلب مشروع (تأهيل/تشطيب/بناء/تملّك)، يتابع حالته، يعدّله أو يلغيه، ويرى تقدّم التنفيذ بعد الموافقة. |
| **شركة عقارية (Investor)** | تتصفح "الفرص" (المشاريع المنشورة بعد مراجعة الإدارة)، وتبدي رغبتها بالعمل على مشروع معيّن. |
| **مشرف (Supervisor)** | صلاحيات مراجعة ومتابعة داخل لوحة الإدارة. |
| **مدير المنصة (Admin)** | يوافق/يرفض الطلبات، ينشرها للشركات، يربط الطلب بالشركة المناسبة، يحدّث نسبة إنجاز المشروع، ويدير إعدادات العمولة. |

الصلاحيات مطبّقة على مستوى قاعدة البيانات نفسها عبر **Row Level Security (RLS)** في Supabase، وليس فقط في واجهة الاستخدام — أي أن أي محاولة وصول غير مصرّح بها تُرفض من قاعدة البيانات مباشرة حتى لو تم تجاوز الواجهة.

## 3. رحلة الطلب (Request Lifecycle)

```
تقديم الطلب  →  review (قيد المراجعة)
                    │
          إدارة المنصة تراجع الطلب
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   published                rejected
 (منشور للشركات)             (مرفوض)
        │
   شركة عقارية تبدي رغبتها
        │  (إشعار تلقائي لصاحب العقار)
        ▼
     matched
  (تم الربط بشركة)
        │
        ▼
  in_progress
 (التنفيذ جارٍ، مع نسبة إنجاز %)
        │
        ▼
   completed
  (اكتمل المشروع)
```

صاحب العقار يستطيع **تعديل أو إلغاء طلبه** في أي وقت من صفحة "طلباتي" طالما لم يُغلق المشروع.

## 4. صفحات المنصة (Pages)

| المسار | الوصف |
|---|---|
| `/` | الصفحة الرئيسية — تعريف بالمنصة وأحدث المشاريع. |
| `/opportunities` | فرص الاستثمار — قائمة الطلبات المنشورة (`published`) مع فلاتر بحث، مخصصة للشركات العقارية. |
| `/new-request` | تقديم طلب مشروع جديد (صاحب العقار يختار نوع الطلب: تأهيل وترميم / تشطيب / بناء جديد / تملّك عقار جديد). |
| `/requests` | "طلباتي ومشاريعي" — كل طلبات المستخدم صاحب العقار، مع تعديل/إلغاء الطلب، ومتابعة نسبة الإنجاز للمشاريع الجارية. |
| `/account` | الحساب الشخصي والمستندات (رفع مستندات إثبات الملكية عبر Supabase Storage). |
| `/notifications` | إشعارات المستخدم (تحديثات الطلب، اهتمام شركة عقارية، تحديث حالة المشروع). |
| `/admin` | لوحة إدارة المنصة (مراجعة/نشر/رفض الطلبات، الربط بالشركات، تحديث نسبة الإنجاز، إعدادات العمولة). خاص بالأدمن/المشرف فقط. |
| `/auth` | تسجيل الدخول / إنشاء حساب (بريد إلكتروني + كلمة مرور، أو Google OAuth). |

## 5. أنواع طلبات المشاريع

1. **عقار يحتاج تأهيل وترميم** — عقار متضرر.
2. **عقار يحتاج تشطيب** — عقار غير متضرر يحتاج لمسة نهائية.
3. **بناء عقار جديد** — تشييد وبناء من الصفر.
4. **تملّك عقار جديد** — رغبة العميل في امتلاك عقار جديد بالكامل.

## 6. الإشعارات (Notifications)

يُطلق نظام إشعارات تلقائي عبر **PostgreSQL trigger** (`notify_owner_on_interest`) عند إبداء شركة عقارية اهتمامها بطلب: يُنشأ إشعار فوري لصاحب العقار في جدول `notifications` يظهر في صفحة "الإشعارات". الإدارة أيضاً تُرسل إشعارات عند نشر الطلب للشركات أو تحديث حالته.

## 7. البنية التقنية (Tech Stack)

| الطبقة | التقنية |
|---|---|
| Frontend | React 19، TanStack Start / TanStack Router، Tailwind CSS 4، خط Cairo، دعم RTL كامل، Dark/Light Mode |
| إدارة الحالة والبيانات | TanStack Query |
| Backend / قاعدة البيانات | Supabase — PostgreSQL + Auth + Storage + Row Level Security |
| المصادقة | Supabase Auth (بريد إلكتروني/كلمة مرور + Google OAuth) |
| رفع الملفات | Supabase Storage (bucket خاص `documents`، كل مستخدم يصل لملفاته فقط، والإدارة تصل للجميع) |
| البناء والنشر | Vite + Nitro، مُهيّأ افتراضياً لـ Cloudflare Workers (`preset: cloudflare-module`) |
| الأيقونات | lucide-react + أيقونات SVG مخصّصة لمنصات التواصل الاجتماعي (`src/components/SocialIcons.tsx`) |

## 8. قاعدة البيانات (Schema Overview)

الجداول الرئيسية (تفاصيلها الكاملة في `supabase/migrations/`):

- **`profiles`** — بيانات المستخدم الأساسية (الاسم، نوع الحساب: صاحب عقار/شركة عقارية...).
- **`user_roles`** — أدوار المستخدم (admin/supervisor) بمعزل عن جدول `profiles` لأسباب أمنية (لمنع تصعيد الصلاحيات ذاتياً).
- **`property_requests`** — طلبات المشاريع: النوع، المدينة، الحي، الوصف، القيمة التقديرية، حالة الطلب (`status`)، نسبة الإنجاز، الشركة المرتبطة، إلخ.
- **`funding_interests`** — سجل اهتمام الشركات العقارية بطلب معيّن.
- **`documents`** — مستندات إثبات الملكية المرفوعة لكل طلب.
- **`notifications`** — إشعارات المستخدمين.
- **`activity_logs`** — سجل نشاط للمراجعة والتدقيق من قبل الإدارة.

كل التغييرات على قاعدة البيانات موثّقة كملفات SQL مرتّبة زمنياً في `supabase/migrations/`، وتُطبّق بالترتيب الزمني لاسم الملف.

## 9. الإعداد والتشغيل محلياً (Local Setup)

```bash
npm install
cp .env.example .env   # ثم عدّل القيم بمعلومات مشروع Supabase الخاص بك
npm run dev             # http://localhost:8080
```

متغيرات البيئة المطلوبة (من supabase.com → Project Settings → API):

```
SUPABASE_PROJECT_ID=
SUPABASE_PUBLISHABLE_KEY=
SUPABASE_URL=
VITE_SUPABASE_PROJECT_ID=
VITE_SUPABASE_PUBLISHABLE_KEY=
VITE_SUPABASE_URL=
```

## 10. تطبيق قاعدة البيانات على مشروع Supabase جديد

1. أنشئ مشروعاً جديداً على [supabase.com](https://supabase.com).
2. نفّذ كل ملفات `supabase/migrations/*.sql` **بترتيب اسم الملف تصاعدياً** عبر SQL Editor، أو عبر Supabase CLI:
   ```bash
   supabase link --project-ref <project-ref>
   supabase db push
   ```
3. أنشئ Storage bucket باسم `documents` (Private) — سياسات الوصول (RLS) الخاصة به معرّفة مسبقاً ضمن الـ migrations.
4. لتفعيل تسجيل الدخول عبر Google: من `Authentication → Providers → Google` في Supabase، فعّل المزود وأدخل Client ID/Secret من Google Cloud Console، وأضف رابط الموقع ضمن Redirect URLs.

## 11. البناء والنشر (Build & Deploy)

```bash
npm run build     # الإخراج في .output/ (هدف Cloudflare Workers عبر nitro)
npm run preview   # معاينة نسخة البناء محلياً
```

للنشر على Cloudflare Workers:
```bash
npx wrangler deploy .output/server/index.mjs --config .output/server/wrangler.json
```

لاستضافة Node.js عادية بدلاً من Cloudflare: غيّر `defaultPreset: "cloudflare-module"` إلى `"node-server"` في `vite.config.ts`، ثم `npm run build` وشغّل `.output/server/index.mjs` مباشرة بـ Node.

## 12. سجل التحديثات المهمة (Changelog)

- **إصلاح خطأ "تعذر التحديث"**: قيد `property_requests_status_check` كان لا يسمح بحالتي `in_progress` و`completed` رغم استخدامهما في لوحة الإدارة عند تحديث نسبة الإنجاز أو إكمال المشروع. تم توسيع القيد.
- **إصلاح إشعار "شركة عقارية مهتمة بطلبك"**: كان نص العنوان بعلامتي اقتباس مزدوجتين داخل دالة PostgreSQL (تُفسَّر كاسم عمود لا كنص)، ما كان يُفشل الإدراج بصمت. تم إصلاحه.
- **إصلاح صفحة "طلباتي"**: كانت تعرض زر المستثمر ("نريد العمل على هذا المشروع") خطأً على طلبات صاحب العقار نفسه. استُبدل بزرَي **تعديل الطلب** و**إلغاء الطلب**.
- **إزالة الاعتماد على Lovable بالكامل**: تسجيل الدخول بـ Google أصبح مباشرة عبر Supabase OAuth، `vite.config.ts` أصبح إعداداً قياسياً بدون حزم `@lovable.dev/*`، وتقرير الأخطاء أصبح بسيطاً ومستقلاً — المشروع الآن مستقل بالكامل وجاهز للتسليم.
- **إضافة روابط التواصل الاجتماعي** في الفوتر: Instagram، TikTok، X، Facebook، WhatsApp، Snapchat، YouTube (`src/components/Footer.tsx` و`src/components/SocialIcons.tsx`).

## 13. ملاحظات للمطوّر القادم

- التزم بنفس نمط الصلاحيات: أي منطق حساس (من يرى ماذا، من يعدّل ماذا) يجب أن يُطبَّق في **RLS policy** على مستوى قاعدة البيانات، وليس فقط بإخفاء عنصر في الواجهة.
- عند إضافة حالة جديدة لـ `property_requests.status`، حدّث أيضاً قيد `property_requests_status_check` في migration جديد (نفس الخطأ الذي تم إصلاحه سابقاً).
- روابط التواصل الاجتماعي في الفوتر لا تزال تحتاج تحديث ببيانات الحسابات الرسمية النهائية إن تغيّرت.
